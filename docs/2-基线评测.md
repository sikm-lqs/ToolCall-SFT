# 2. 基线评测

目标是在单张 **A100-SXM4-40GB** 上，为未微调、未量化的 `Qwen/Qwen3.5-2B` 与 `Qwen/Qwen3.5-0.8B` 建立工具调用质量与服务性能基线，并交付 **Markdown + HTML 基线评测报告**及 SwanLab 云端记录。开始前先完成[服务器环境安装与双模型 smoke](0-服务器环境安装.md#7-双模型-smoke-验收)。

---

## 1. 评测范围与常见坑点

基线按 **2B → 0.8B** 顺序串行测试，每款模型执行 **BFCL V4 → API-Bank → τ²-Bench**。

| 评测集 | 基线范围与命令 Profile | 重点防坑说明 |
| --- | --- | --- |
| **BFCL V4** | `bfcl-eval==2026.3.23`，**`--profile no-web`**（4,906 题：Non-Live 1,390 + Live 2,251 + Multi-turn 800 + Memory 465，另含 111 个 Memory 初始化） | 1. **跳过 Web Search（200 题）**：强依赖 `SERPAPI_API_KEY` 与外网且搜索结果随时间漂移，不利于后训练复现对比。<br>2. **Memory（465 题）耗时高、基线区分度低**：基线阶段跑一遍 `no-web` 留底；**后续 SFT/OPD/GRPO 高频消融改用下方 8 子类子集（1,840 题）**。<br>3. **`no_web_weighted_accuracy`**：官方 `Overall Acc` 中 Web Search 占 20%，除以 `80` 归一化仅供无网搜口径内横比。 |
| **API-Bank** | **`--profile full`**（314 段对话：753 调用 + 528 回复） | 全量仅需 ~2 分钟，直接跑完作辅助回归检查。**注意**：上游 Checker 的 `oracle_accuracy` 在 L1/L2 仅约 `86.9% / 65.5%`，L2 原生 FC 受工具发现覆盖率限制（~89.1%），**不作为核心刷分主榜**。 |
| **τ²-Bench** | `v0.2.0`，**`--profile full`**（Retail 114 + Airline 50 + Telecom 114，共 278 题，每题 1 次） | 1. **严禁自模拟**：2B/0.8B 既当 agent 又当 user 会死循环打满 `MAX_STEPS` 得 0 分，**必须固定独立强 User Simulator**（全程锁定同一模型、版本与 `temperature=0`）。<br>2. **控制并发**：受外部模拟器延迟与限流约束，建议 `--concurrency 3~8`，勿盲目拉高；开跑前可用 `--domains retail --limit 10` 先探步数与限流。 |

### 后续高频迭代：BFCL 高性价比子集（1,840 题）

SFT / OPD / GRPO 调参阶段跳过耗时的 `memory_*`、冷门的 Java/JS 以及重复度高的 Live 简单题，固定跑以下 8 类（几分钟出分），定型后再补全量 `no-web`：

```bash
.venv/bin/toolcall-eval bfcl-v4 --categories \
  simple_python multiple parallel parallel_multiple irrelevance \
  multi_turn_base multi_turn_miss_func multi_turn_miss_param \
  --model "$model" --base-url "$base_url" --concurrency 64 --gpu-index 0
```

## 2. 统一服务与评测参数

除模型权重外，2B 与 0.8B 严格使用相同引擎与采样配置：

| 层级 | 参数设定 | 说明 |
| --- | --- | --- |
| 硬件与排布 | 单张 A100-SXM4-40GB；单模型串行独占 | 评测期间不跑训练或其他 GPU 任务 |
| 服务与引擎 | `vllm==0.19.1`（`cu129`）、驱动 `595.84`、BF16 不量化、`--language-model-only` | 跳过多模态视觉分支节省显存 |
| 上下文与显存 | `--max-model-len 32768`、`--gpu-memory-utilization 0.85`、`--no-enable-prefix-caching` | `10240` 上下文会在 BFCL 多轮与 τ² 触发大量 `context_rejection`，`32768` 可彻底消除 |
| 调度与并发 | `--max-num-seqs 128`、`--max-num-batched-tokens 8192`；BFCL / API-Bank 客户端 `--concurrency 64~96`，τ² `--concurrency 3~8` | 若 `resources.jsonl` 出现 `preemptions > 0` 或 KV Cache 逼近 90%，则下调并发至 `48` |
| 工具与解码 | Native FC、`--enable-auto-tool-choice --tool-call-parser qwen3_coder`、`enable_thinking=false`、`temperature=0`、`--max-tokens 1024`、`--timeout 180` | 关思考下 `1024` 足以覆盖调用与回复（仅 ~1% 截停）并防止死循环拖慢批次；若后续开启思考需提至 `2048+` |
| τ² 模拟器 | 独立 OpenAI 兼容强模型端点、`--user-temperature 0`、`--seed 300`、`--max-steps 200` | 2B 与 0.8B 必须共用同一模拟器设置 |

## 3. 执行命令

先在推理终端按[安装文档 §5.3](0-服务器环境安装.md#53-启动单个受测模型服务)启动模型并完成探针检查；再在评测终端执行：

```bash
model=Qwen/Qwen3.5-2B
base_url=http://127.0.0.1:18003/v1
: "${CHECKPOINT_REVISION:?填入模型快照哈希或 commit}"
: "${TAU2_USER_MODEL:?填入已审核的独立用户模拟器模型名}"
: "${TAU2_USER_BASE_URL:?填入独立模拟器 /v1 地址}"

common=(--model "$model" --base-url "$base_url" --variant baseline
  --checkpoint-revision "$CHECKPOINT_REVISION" --gpu-index 0
  --max-tokens 1024 --temperature 0 --timeout 180)

# 1. BFCL V4 (no-web, 4,906 题)
.venv/bin/toolcall-eval bfcl-v4 --profile no-web "${common[@]}" --concurrency 64

# 2. API-Bank (full, 1,281 步)
.venv/bin/toolcall-eval api-bank --profile full "${common[@]}" --concurrency 96

# 3. τ²-Bench (full, 278 题)
.venv/bin/toolcall-eval tau2 --profile full "${common[@]}" --concurrency 3 \
  --domains retail airline telecom --trials 1 --max-steps 200 --seed 300 \
  --user-model "$TAU2_USER_MODEL" --user-base-url "$TAU2_USER_BASE_URL" --user-temperature 0
```

切换到 `Qwen/Qwen3.5-0.8B` 时重启 vLLM 服务并同步更新 `model` 与 `CHECKPOINT_REVISION`，其余参数保持不变。

## 4. 必记指标与典型错题归因

每次运行后检查 `summary.json` 的 `status == "completed"`，并按以下五个维度收集指标：

| 维度 | 核心指标 | 数据源 |
| --- | --- | --- |
| **正确率 / 分数** | BFCL：`no_web_weighted_accuracy`、`microaccuracy`、Non-Live / Live / Multi-turn / Memory 分项；<br>API-Bank：L1/L2/L3 调用准确率、L2 覆盖率与条件准确率、ROUGE-L；<br>τ²：三域 `task_success_rate`（`pass_hat_1`）、`domain_mean_task_success_rate`、`average_reward` | `summary.json`、`score/` |
| **时间开销** | 端到端 `wall_seconds`、推理/模拟耗时（`generation_seconds` / `simulation_seconds`）、评分耗时 `scoring_seconds` | `summary.json` |
| **吞吐与延迟** | 成功请求输入/输出 token 总数、`output_tokens_per_second`、`total_tokens_per_second`、`latency_p95_seconds`（τ² 单看 `agent_` 前缀） | `summary.json`、`model-requests.jsonl` |
| **显卡与服务压力** | 空闲显存、整卡峰值 `peak_gpu_used_mib`、GPU 利用率峰值、KV Cache 峰值（`peak_kv_cache_usage_perc × 100%`）、运行/排队请求峰值、`preemptions` | `resources.jsonl`、`summary.json` |

### 典型错题两分法（报告必含）

分析基线失败案例时，**必须区分“系统/基础设施问题”与“真实 LLM 能力缺陷”**，避免误把工程 Bug 当成模型问题去训：

1. **系统 / 基础设施错误（需修环境/参数，不靠训练解决）**
   - `request_errors`（超时、HTTP 4xx/5xx、连接中断）
   - `context_rejections`（输入+输出超过 `max_model_len`）
   - `length_stops` / `output_cap_stops`（被 `max_tokens` 硬截断）
   - 评测器或后端异常（如 API-Bank `backend_resource_missing` / `tool_exception`、τ² `MAX_ERRORS` 或模拟器 API 报错）
2. **真实 LLM 能力错误（后续 SFT / OPD / GRPO 的核心改进靶点）**
   - **漏调工具**：该调用函数时只输出纯文本解释（`missing_tool_call` / `wrong_count`）
   - **选错工具 / 幻觉工具**：选错 API（`wrong_tool`）或调用 `tools` 外不存在的函数（`tool_not_offered`）
   - **幻觉调工具（拒答失败）**：无合适工具（`irrelevance`）或强制禁调（`tool_choice="none"`）时仍输出工具调用或裸 `<tool_call>` 文本
   - **参数错误**：必填参数缺失、类型错误、枚举/嵌套结构错误
   - **多轮与交互缺陷**：缺参不追问（`miss_param`）、缺工具不识别（`miss_func`）、多轮死循环打满 `MAX_STEPS`、违反业务 Policy 导致数据库终局状态不符（`reward=0`）

## 5. 交付报告生成（Markdown + HTML）

基线跑完后，使用仓库内置工具一键汇总多组运行结果，同时生成 **Markdown 报告**与带交互图表的**独立 HTML 报告**：

```bash
.venv/bin/toolcall-baseline-report \
  --runs <bfcl_2b_dir> <apibank_2b_dir> <tau2_2b_dir> <bfcl_08b_dir> <apibank_08b_dir> <tau2_08b_dir> \
  --out-md reports/baseline-report.md \
  --out-html reports/baseline-report.html
```

不传 `--runs` 时可加 `--auto` 自动扫描 `runs/eval/` 下每个 `(benchmark, model)` 最新的已保存运行目录。报告自动包含：范围核对表、分数矩阵、时间/吞吐/显卡压力表、KV Cache 与 GPU 趋势图，以及拆分为**系统错误**与**真实 LLM 错误**的典型错题实例。

## 6. SwanLab 云端记录与建项排查

每次调用 `toolcall-eval` 结束时都会自动执行 `report_run(..., upload=True)`，以 `mode="online"` 将配置、标量指标与图表上报到 SwanLab Cloud 的 **`toolcall-sft`** 项目（按 `benchmark` 分组）。

### 为什么网页上还没看到 `toolcall-sft` 项目？

1. **项目仅在首次成功 `online` 上报时创建**：此前本地探索运行（检查 `runs/eval/*/*/*/swanlab.json`）均为 `"mode": "local"` 离线模式，从未向云端推送；而新服务器若尚未登录或尚未完整走完一次评测收尾，云端就不会出现该项目。
2. **检查登录凭据与工作空间**：
   - 在服务器运行 `.venv/bin/swanlab login`（或配置环境变量 `SWANLAB_API_KEY`）；
   - 如使用团队空间，确认环境变量 `SWANLAB_WORKSPACE` 与网页端当前所在空间一致。
3. **验证建项 / 补传历史运行**：对任意已完成且本地保存的运行目录执行一次补传即可立即在云端看到项目：

```bash
.venv/bin/toolcall-eval report "<run_dir>" --swanlab online
```
