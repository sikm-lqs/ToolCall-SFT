# 2. 基线评测

目标是在单张 **A100-SXM4-40GB** 上，为未微调、未量化的 `Qwen/Qwen3.5-2B` 与 `Qwen/Qwen3.5-0.8B` 建立工具调用质量与服务性能基线，并交付 **Markdown + HTML 基线评测报告**及 SwanLab 云端记录。开始前先完成[服务器环境安装与双模型 smoke](0-服务器环境安装.md#7-双模型-smoke-验收)。

> **本版参数修订依据（基于首轮 2B 实测诊断）：**
> 1. 首轮 `no-web` 输入输出比达 `61:1`（98.26M vs 1.61M），82% 时间耗在 `multi_turn` 重复前缀 prefill，而 KV Cache 峰值仅 `29.8%` → 改为开启 **`--enable-prefix-caching`**，并将客户端并发提至 `128`、vLLM 提至 `--max-num-seqs 256` / `--max-num-batched-tokens 32768`。
> 2. `multi_turn_long_context` 最长 prompt 达 `31,745`，加 `1,024` 输出超出 `32,768` 触发 44 次 400 拒绝 → 上下文窗口升至 **`--max-model-len 49152`**。
> 3. BFCL `memory_*` 耗时高且 2B 真实水平为 0%，`web_search_*` 受外网与配额漂移影响 → 后续统一采用 **`--profile core`**（Non-Live + Live + Multi-turn，17 类共 4,441 题），不再跑 Web Search 与 Memory。

## 1. 评测范围与防坑说明

基线按 **2B → 0.8B** 顺序串行测试；**当前阶段先执行 BFCL V4 (`core`) 与 API-Bank (`full`)，τ²-Bench 暂缓执行**（待补充独立强 User Simulator 的 API Key 与模型服务后再补跑）。

| 评测集 | 基线范围与命令 Profile | 状态与防坑说明 |
| --- | --- | --- |
| **BFCL V4** | `bfcl-eval==2026.3.23`，**`--profile core`**（4,441 题：Non-Live 1,390 + Live 2,251 + Multi-turn 800） | **立即执行。**<br>1. **跳过 Web Search 与 Memory**：只测直接反映单轮、并行、拒答与多轮交互能力的 17 类。<br>2. **`core_weighted_accuracy`**：官方 V4 权重中 Non-Live(10)+Live(10)+Irrelevance(10)+Multi-turn(30)=60%，除以 `60` 归一化仅作无 Agentic 子集口径内横比。 |
| **API-Bank** | **`--profile full`**（314 段对话：753 调用 + 528 回复） | **立即执行（2B 若已完成可保留）。** 约 2 分钟跑完，沿用 `concurrency=96` 保持不变即可。**注意**：上游 Checker 的 `oracle_accuracy` 在 L1/L2 仅约 `86.9% / 65.5%`，L2 原生 FC 受工具可见率限制（~89.1%），仅作回归参考。 |
| **τ²-Bench** | `v0.2.0`，**`--profile full`**（Retail 114 + Airline 50 + Telecom 114，共 278 题，每题 1 次） | **暂缓执行（待补模拟器服务与 `TOOLCALL_USER_API_KEY`）。**<br>1. **严禁自模拟**：2B/0.8B 既当 agent 又当 user 会死循环打满 `MAX_STEPS` 得 0 分，必须等独立强 User Simulator 就绪后再跑。<br>2. **控制并发**：启用后保持 `--concurrency 3~8`，勿套用 BFCL 的 128 并发。 |

### 后续高频迭代：BFCL 高性价比子集（1,840 题）

SFT / OPD / GRPO 调参阶段跳过 `simple_java`/`simple_javascript`、`multi_turn_long_context` 及重复度高的 Live 简单题，固定跑以下 8 类，定型后再补跑完整 `--profile core`：

```bash
.venv/bin/toolcall-eval bfcl-v4 --categories \
  simple_python multiple parallel parallel_multiple irrelevance \
  multi_turn_base multi_turn_miss_func multi_turn_miss_param \
  --model "$model" --base-url "$base_url" --concurrency 128 --gpu-index 0
```

## 2. 统一服务与评测参数

除模型权重外，2B 与 0.8B 严格使用同一套 vLLM 与采样配置：

| 层级 | 参数设定 | 说明 |
| --- | --- | --- |
| 硬件与排布 | 单张 A100-SXM4-40GB；单模型串行独占 | 评测期间不跑训练或其他 GPU 任务 |
| 服务与引擎 | `vllm==0.19.1`（`cu129`）、驱动 `595.84`、BF16 不量化、`--language-model-only` | 跳过多模态视觉分支节省显存 |
| 上下文与缓存 | `--max-model-len 49152`、`--gpu-memory-utilization 0.85`、**`--enable-prefix-caching`** | 48K 上下文消除 `multi_turn_long_context` 的 44 次截断拒绝；Prefix Caching 大幅加速多轮重复前缀 |
| 调度与并发 | **`--max-num-seqs 256`**、**`--max-num-batched-tokens 32768`**；BFCL `--concurrency 128`，API-Bank `--concurrency 96`，τ² `--concurrency 3~8` | 针对 Prefill 主导负载拉满吞吐；若出现 `preemptions > 0` 再回调并发 |
| 工具与解码 | Native FC、`--enable-auto-tool-choice --tool-call-parser qwen3_coder`、`enable_thinking=false`、`temperature=0`、`--max-tokens 1024`、`--timeout 180` | 关思考下 `1024` 足以覆盖调用与回复（仅 ~1% 截停）；若后续开启思考需提至 `2048+` |
| τ² 模拟器 | 独立 OpenAI 兼容强模型端点、`--user-temperature 0`、`--seed 300`、`--max-steps 200` | 2B 与 0.8B 必须共用同一模拟器设置 |

## 3. 服务启动与执行命令

### 3.1 启动受测模型 vLLM 服务（推理终端）

```bash
set -o pipefail
model=Qwen/Qwen3.5-2B
snapshot="$HOME/.cache/modelscope/models/Qwen--${model#*/}/snapshots/master"
model_slug="${model#*/}"
service_dir="runs/services/${model_slug,,}/$(date -u +%Y%m%dT%H%M%S.%NZ)"
mkdir -p "$service_dir"

runs/envs/serve/bin/vllm serve "$snapshot" --served-model-name "$model" \
  --host 127.0.0.1 --port 18003 --tensor-parallel-size 1 --dtype bfloat16 \
  --language-model-only --max-model-len 49152 --gpu-memory-utilization 0.85 \
  --max-num-seqs 256 --max-num-batched-tokens 32768 \
  --enable-auto-tool-choice --tool-call-parser qwen3_coder \
  --generation-config vllm --seed 0 --enable-prefix-caching \
  2>&1 | tee "$service_dir/vllm.log"
```

### 3.2 执行基线评测（评测终端）

当前阶段先跑 BFCL V4 (`core`) 与 API-Bank (`full`)：

```bash
model=Qwen/Qwen3.5-2B
base_url=http://127.0.0.1:18003/v1
: "${CHECKPOINT_REVISION:?填入模型快照哈希或 commit}"

common=(--model "$model" --base-url "$base_url" --variant baseline
  --checkpoint-revision "$CHECKPOINT_REVISION" --gpu-index 0
  --max-tokens 1024 --temperature 0 --timeout 180)

# 1. BFCL V4 (core: Non-Live + Live + Multi-turn, 4,441 题)
.venv/bin/toolcall-eval bfcl-v4 --profile core "${common[@]}" --concurrency 128

# 2. API-Bank (full, 1,281 步；若 2B 已完成可直接保留)
.venv/bin/toolcall-eval api-bank --profile full "${common[@]}" --concurrency 96
```

待补充独立 User Simulator 的 `TOOLCALL_USER_API_KEY`、`TAU2_USER_MODEL` 与 `TAU2_USER_BASE_URL` 后，再补跑 τ²-Bench：

```bash
# 3. τ²-Bench (full, 278 题；待独立模拟器就绪后执行)
: "${TOOLCALL_USER_API_KEY:?填入独立模拟器的 API Key}"
: "${TAU2_USER_MODEL:?填入已审核的独立用户模拟器模型名}"
: "${TAU2_USER_BASE_URL:?填入独立模拟器 /v1 地址}"

.venv/bin/toolcall-eval tau2 --profile full "${common[@]}" --concurrency 3 \
  --domains retail airline telecom --trials 1 --max-steps 200 --seed 300 \
  --user-model "$TAU2_USER_MODEL" --user-base-url "$TAU2_USER_BASE_URL" --user-temperature 0
```

切换到 `Qwen/Qwen3.5-0.8B` 时重启 vLLM 服务并同步更新 `model` 与 `CHECKPOINT_REVISION`，其余参数保持不变。

## 4. 必记指标与典型错题归因

每次运行后检查 `summary.json` 的 `status == "completed"`，并按以下五个维度收集指标：

| 维度 | 核心指标 | 数据源 |
| --- | --- | --- |
| **正确率 / 分数** | BFCL：`core_weighted_accuracy`、`microaccuracy`、Non-Live / Live / Multi-turn 分项；<br>API-Bank：L1/L2/L3 调用准确率、L2 覆盖率与条件准确率、ROUGE-L；<br>τ²：三域 `task_success_rate`（`pass_hat_1`）、`domain_mean_task_success_rate`、`average_reward` | `summary.json`、`score/` |
| **时间开销** | 端到端 `wall_seconds`、推理/模拟耗时（`generation_seconds` / `simulation_seconds`）、评分耗时 `scoring_seconds` | `summary.json` |
| **吞吐与延迟** | 成功请求输入/输出 token 总数、`output_tokens_per_second`、`total_tokens_per_second`、`latency_p95_seconds`（τ² 单看 `agent_` 前缀） | `summary.json`、`model-requests.jsonl` |
| **显卡与服务压力** | 空闲显存、整卡峰值 `peak_gpu_used_mib`、GPU 利用率峰值、KV Cache 峰值（`peak_kv_cache_usage_perc × 100%`）、运行/排队请求峰值、`preemptions` | `resources.jsonl`、`summary.json` |

### 典型错题两分法（报告必含）

分析基线失败案例时，**必须区分“系统/基础设施错误”与“真实 LLM 能力错误”**：

1. **系统 / 基础设施错误（需修环境/参数，不靠训练解决）**
   - `request_errors`（超时、HTTP 4xx/5xx、连接中断）
   - `context_rejections`（输入+输出超过 `max_model_len`）
   - `length_stops` / `output_cap_stops`（被 `max_tokens` 硬截断）
   - 评测器或后端异常（如 API-Bank 上游报错、τ² `MAX_ERRORS` 或模拟器 API 报错）
2. **真实 LLM 能力错误（后续 SFT / OPD / GRPO 的核心改进靶点）**
   - **漏调工具**：该调用函数时只输出纯文本解释（`missing_tool_call` / `wrong_count`）
   - **选错工具 / 幻觉工具**：选错 API（`wrong_tool`）或调用 `tools` 外不存在的函数（`tool_not_offered`）
   - **幻觉调工具（拒答失败）**：无合适工具（`irrelevance`）或强制禁调（`tool_choice="none"`）时仍输出工具调用或裸 `<tool_call>` 文本
   - **参数错误**：必填参数缺失、类型错误、枚举/嵌套结构错误
   - **多轮与交互缺陷**：缺参不追问（`miss_param`）、缺工具不识别（`miss_func`）、多轮死循环打满 `MAX_STEPS`、违反业务 Policy 导致数据库终局状态不符（`reward=0`）

## 5. 交付报告生成（Markdown + HTML）

基线跑完后使用内置工具一键输出 **Markdown 报告**与带图表的**独立 HTML 报告**：

```bash
.venv/bin/toolcall-baseline-report \
  --runs <bfcl_2b_dir> <apibank_2b_dir> <bfcl_08b_dir> <apibank_08b_dir> \
  --out-md reports/baseline-report.md \
  --out-html reports/baseline-report.html
```

*(后续补齐 τ²-Bench 后，将 `<tau2_2b_dir>` 与 `<tau2_08b_dir>` 一并传入或直接用 `--auto` 重新生成即可。)*

不传 `--runs` 时可加 `--auto` 自动选取 `runs/eval/` 下每个 `(benchmark, model)` 最新的已保存运行目录。

## 6. SwanLab 云端记录与建项排查

每次 `toolcall-eval` 结束时都会自动执行 `report_run(..., upload=True)`，以 `mode="online"` 将配置、标量指标与图表上报到 SwanLab Cloud 的 **`toolcall-sft`** 项目（按 `benchmark` 分组）。

- **为什么网页上还没看到 `toolcall-sft` 项目？** 此前本地旧运行均为 `"mode": "local"` 离线记录；项目仅在服务器首次完成登录并成功 `online` 上报时才会在云端建立。
- **检查登录与空间**：运行 `.venv/bin/swanlab login`（或配置 `SWANLAB_API_KEY`）；若使用团队空间，确认 `SWANLAB_WORKSPACE` 环境变量与网页一致。
- **验证建项 / 补传历史运行**：
  ```bash
  .venv/bin/toolcall-eval report "<run_dir>" --swanlab online
  ```
