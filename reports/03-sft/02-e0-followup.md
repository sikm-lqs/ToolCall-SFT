## 数据和划分复核

| 分桶 | 3,000 条训练 | 500 条验证 |
| --- | ---: | ---: |
| xLAM 并行工具调用 | 1,000 | 180 |
| xLAM 单次工具调用 | 500 | 100 |
| ToolACE 单轮或并行调用 | 750 | 140 |
| ToolACE 带工具返回的对话 | 400 | 40 |
| ToolACE 不调用 / 追问 | 350 | 40 |

- 两个切分来自同一个清洗池，但先用 seed 42 按桶留出验证集，再独立从剩余池构建 smoke 与正式 27k。按仓库签名（用户轮文本 + 排序后的工具名）复核，smoke 与 val 交集 0，smoke 与正式训练集共有 1,888 个签名；smoke 不是从正式训练 JSONL 直接截取。只比对用户轮文本时，smoke 与 val 有 2 个共享键，因此不把签名隔离表述为语义零重叠。
- smoke 有 2,522,669 个输入 token（均值 840.9），其中 400,989 个 assistant 监督 token；3,000 条记录打包为 311 个序列。350 条无调用记录中，65 条候选列表为空，285 条有候选；后者混有工具不适用和缺参追问，不等于 285 条 BFCL 式不匹配负例。
- 500 条验证样本只做 teacher-forced 验证损失 / token 指标，E0 在 step 20 和 39 验证并保存；step 39 被选中部署。外部 BFCL 8 类 1,840 题只用于部署后快筛，不参与本仓库的训练与验证切分。

## BFCL 拒调：实际保存的输出

下表来自 BFCL 原生 FC 的 `result` 和 `score` 文件，且与 `model-requests.jsonl` 中的 `finish_reason=tool_calls` 逐题交叉验证。保存的是 API 返回后经 handler 记录的名称/参数，不是解析前的 XML；自然语言回复未在这些 FC 结果行保留。

| 题目 ID | 用户任务（意译） | E0 记录的实际调用 |
| --- | --- | --- |
| `irrelevance_0` | 求底为 10 m、高为 5 m 的三角形面积 | `determine_body_mass_index({"weight":10,"height":5})` |
| `irrelevance_6` | 求宽 5 m、长 7 m 的矩形面积 | `draw_circle({"radius":5,"unit":"m"})`、`draw_circle({"radius":7,"unit":"m"})` |
| `irrelevance_9` | 求定积分（被积函数为 x²） | `CalculateTax({"annual_income":100000,"tax_rate":0.2,"other_deductions":10000})` |

这三题基座结构化调用均为 `[]`。240 题里，E0 的 180 个 `tool_calls` ID 与 180 个 `irrelevance_error:decoder_success` ID 完全一致；另有 59 个 `stop`、1 个 `length`，无请求错误。BFCL 此项只判「是否有可解码的调用」，不评价自然语言答案正确性。证据支持这些误调是真实行为，不支持「是 HTTP 失败或评分器误判造成的」。

**补记服务日志异常：** E0 有 1 次 `qwen3_coder` 提取函数 XML 时的 `ValueError: substring not found`；vLLM 捕获后按普通文本返回，不中断请求。基线服务日志也记录过 1 次同类异常。现有并发日志没有足够信息定位到某个 benchmark ID，也未修复上游解析器。它不是上述 180 个带结构化调用的失败的解释。

## A100 吞吐短测

使用正式 2B YAML 的配置，从已冻结且打乱的训练集取前 1,400 条，每组从同一底座运行 4 个优化器步；有效 batch 固定 8 个 packed 序列，保留 BF16、8K packing/padding-free、loss mask、LoRA、GPU kernel，关闭评估、周期保存及 SwanLab（不计最后产物写盘）。第 1 步作为预热，以下比较第 2–4 步；这是训练吞吐短测，不是训练效果实验。

| 微批次 × 累积 | 梯度重计算 | 预检 | 平均秒 / 优化器步 | 输入 token/s（约） | PyTorch 峰值 allocated / reserved |
| --- | --- | --- | ---: | ---: | ---: |
| 1 × 8（现配置） | 开 | 原路径通过 | 11.33 | 5,715 | 7.19 / 8.37 GiB |
| 1 × 8 | 关 | 原路径通过 | **8.61** | **7,521** | 33.17 / 34.80 GiB |
| 2 × 4 | 开 | 实验性 fused 预检通过 | 14.25 | 4,544 | 10.23 / 12.72 GiB |
| 4 × 2 | 开 | 实验性 fused 预检通过 | 21.05 | 约 3,080 | 17.36 / 19.59 GiB |

原预检直接执行模型 forward 并产生整批大词表 logits。微批次 2（开或关重计算）以及微批次 4（关重计算）均在其上 OOM，未进入训练。为了区分是预检还是训练本身超限，第二个快照仅在实验脚本里把 GPU forward 探针改成已装 TRL 1.18.2 训练使用的 `fused_lm_head=True` 路径，仍检查 packed 边界和有限 loss。保持重计算开启的 2×4、4×2 均成功反传，但更慢；**未**对关闭重计算的 2×4、4×2 使用 fused 探针复测。正式预检代码没有改动。

现配置训练窗口的 NVML GPU 活跃时间平均约 98%，并非只有约 18% 的算力在使用。7.2 GiB 是 PyTorch allocated 指标，且训练摘要在 GPU 预检后重置峰值，两者都不能推出算力打满程度或预检的显存上限。把空闲显存用来存激活、减少反传重算，比增加微批次有效：本短测每步约快 24%，吞吐约增 32%。单组仅 4 步，正式 2B 候选为 1×8、关闭梯度重计算；先在完整数据的打包与验证路径上复测显存水位和稳定性，再决定改正式 YAML。0.8B 需独立短测，不能直接套用。

短测日志、脚本和显存/利用率采样：`runs/train/sft-perf-2b-20261124T105926Z`、`runs/train/sft-perf-2b-fused-20261124T110307Z`。已回收轻量文件，不拉取权重。
